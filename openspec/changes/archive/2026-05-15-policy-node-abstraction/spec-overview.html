Why this change exists

Problem

Robot learning policies need a first-class DimOS module abstraction so perception, state, and task-conditioned models can be composed into robot stacks without one-off glue code for each policy framework or robot.

DimOS already has typed streams and a centralized ControlCoordinator; this change standardizes how learned policies consume observations and emit coordinator-compatible commands.

No breaking change

Existing coordinator, teleop, and blueprint behavior remain intact. The policy node publishes existing command message types rather than replacing coordinator APIs.

Proposed architecture

Inputs
  • Multi-camera Image streams
  • Latest JointState
  • Plain str task description
→
PolicyNode
  • Builds PolicyObservation
  • Runs selected backend at configured rate
  • Validates command mapping
→
Output
  • JointState.name
  • JointState.position
  • Connects to ControlCoordinator.joint_command

Core models

  • PolicyObservation: camera-name keyed images, joint state, task text, timestamps, optional backend extras.
  • PolicyCommand: tagged command model with initial joint-position output and explicit no-op handling.
  • PolicyNodeConfig: backend name/config, policy rate, camera mapping, joint mapping, command mode, default task description.

Key design decisions

  • Keep framework tensors and feature dictionaries inside backend adapters.
  • Use existing coordinator-native command streams first.
  • Make action-space mapping explicit; never infer semantics from vector shape.
  • Keep model inference outside the coordinator tick loop.

Policy node requirements

Unified observation inputs

The system SHALL provide a policy node module under dimos.manipulation.policy that accepts multi-camera image inputs, latest robot joint state, and a plain string task description.

Scenario: when images, JointState, and task text arrive, the node assembles a policy observation keyed by configured camera/source names.
Scenario: task description is exposed as str, not a LangChain message or custom task message.

Coordinator-compatible joint position commands

The system SHALL support joint position as the reference command output by publishing a JointState with name and position fields compatible with ControlCoordinator.joint_command.

Scenario: backend joint targets become a matching JointState command.
Scenario: no coordinator routing or arbitration changes are required.

Command validation

The system SHALL validate command mode, joint names, and action dimensions before publishing commands.

Scenario: missing, extra, or unmapped action values are rejected.
Scenario: unsupported command families are not published.

Runtime cadence

The system SHALL run policy inference at a configured policy rate using latest available observations and keep model inference outside the ControlCoordinator tick loop.

Scenario: missing required observations cause the node to skip publishing for that step.

Backend registration

Registry

Backend names map to implementations through a shared registry. Unknown backend names fail startup with a clear error.

LeRobot

The lerobot backend adapts DimOS observations into LeRobot inference inputs, runs model selection/postprocessing, and converts outputs into PolicyCommand.

TestPolicy

The test backend emits deterministic sinusoidal joint position commands for configured joints without model files, GPUs, or external robot-learning dependencies.

Policy backend interface

Backends receive PolicyObservation and return PolicyCommand or no-op. Framework-specific tensors, features, and robot action dictionaries remain behind adapter boundaries.

TestPolicy behavior

TestPolicy is configured with joint names, amplitude, frequency, phase, and optional center positions. It exercises the same registry and validation path as LeRobot.

Risks and mitigations

Action-space ambiguity
Mitigation: explicit command mode and action-name mappings in PolicyNodeConfig.
Stale observations
Mitigation: timestamp observations and no-op when required data is incomplete.
Heavy backend dependencies
Mitigation: lazy/optional adapter imports, especially for LeRobot.
Unsafe test motion
Mitigation: explicit low-amplitude TestPolicy parameters and controlled setup guidance.
Multi-camera complexity
Mitigation: configured camera/source names and explicit backend feature-name mapping.
Inference latency
Mitigation: policy node rate control, no coordinator tick-loop changes.
